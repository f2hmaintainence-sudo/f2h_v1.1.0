## Title

`POST /admin/inventory/purchases` always returns 500 — stock can never be received

## Steps to Reproduce

1. `POST /api/v1/admin/inventory/purchases` with
   `{"warehouse_id":"WH-MTEBESZ953A8S7","variant_id":"VRT0NFGWE8WG","quantity":500,"unit_cost":45,"batch_no":"QA-BATCH-001"}`.
2. Retry with the numeric warehouse id (`"warehouse_id": 4`).
3. `GET /api/v1/admin/inventory/purchases`.

## Expected Result

A `purchase_entries` row is created, `stock_balances.available_quantity` increases by 500, and an
immutable `stock_movements` row is written with `movement_type='purchase_in'` and a correct
`quantity_after`.

## Actual Result

Both attempts return HTTP 500 `{"message":"Failed to create purchase entry"}`, and
`GET /admin/inventory/purchases` returns `{"status":true,"data":[],"message":"Purchase entries fetched"}`
— the table is empty. No `stock_balances` row exists for the warehouse.

Two distinct causes, one after the other:
```
1) invalid input syntax for type integer: "WH-MTEBESZ953A8S7"   (22P02)
2) null value in column "id" of relation "purchase_entries" violates not-null constraint (23502)
   Failing row: (null, PUR-1788005365172-RTYI, null, 4, VRT0NFGWE8WG, ...)
```

## Root Cause

1. **Identifier type mismatch.** `purchase_entries.warehouse_id` is `integer`, while every other
   table and the whole API surface use the varchar business key (`warehouses.warehouse_id`,
   e.g. `WH-MTEBESZ953A8S7`). The service passes the business key straight into the integer
   column. `purchase_entries.vendor_id` is `integer` too, with no `vendors` table in the schema at all.

2. **Missing sequence.** `purchase_entries.id` is `integer NOT NULL` with **no default**, and the
   INSERT does not supply it. Even with a numeric warehouse id the insert fails. This is the same
   defect class as `role_assignments.id` (ISS-033); every other table in the schema uses
   `nextval(...)`.

## Affected Files / API / Tables

- `apps/api/src/panels/admin/catalog-inventory/inventory/...` — `createPurchaseEntry`
- Schema: `purchase_entries.id` (no default), `purchase_entries.warehouse_id` / `vendor_id` (`integer`)
- Tables: `purchase_entries`, `stock_balances`, `stock_movements`, `warehouses`

## Recommended Fix

1. `ALTER TABLE purchase_entries ADD GENERATED BY DEFAULT AS IDENTITY` on `id` (or attach a
   sequence and set the default).
2. Align `warehouse_id` with the rest of the schema — change it to `varchar` referencing
   `warehouses.warehouse_id`, or resolve the business key to the numeric id inside the service.
   The former is consistent with `stock_balances`, `stock_movements` and `warehouse_containers`.
3. Same decision for `vendor_id` — either introduce the `vendors` table the code and test plan
   assume, or drop the column (see FU-001).
4. Ensure the handler writes `stock_balances` and `stock_movements` inside one transaction with the
   purchase entry.

## Regression Tests Required

- WH-STK-002 (inter-warehouse transfer, double movement)
- Idempotency/rollback test: a failed movement write must not leave an orphan purchase entry
- E2E-012 (branch → warehouse intake → order assignment)
