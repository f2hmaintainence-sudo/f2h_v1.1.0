## Title

`role_assignments.id` and `purchase_entries.id` are NOT NULL with no default or sequence

## Steps to Reproduce

1. `INSERT INTO role_assignments (user_id, role_id, is_active) VALUES (...)` without `id`.
2. `POST /api/v1/admin/inventory/purchases` (which omits `purchase_entries.id`).
3. Compare with `SELECT column_default FROM information_schema.columns WHERE column_name='id'` across the schema.

## Expected Result

`id` is populated by a sequence/identity, as it is on every other table.

## Actual Result

Both inserts fail with `23502 null value in column "id" ... violates not-null constraint`.

Across the tables checked, every other one has `nextval('<table>_id_seq'::regclass)`:
```
customer_addresses, customer_container_balances, customer_special_prices,
customer_wallet_transactions, delivery_dispatch, delivery_dispatch_items,
delivery_runs, management_staff, order_items, orders, referrals,
stock_balances, subscription_items, subscription_weekly_schedule, subscriptions   -> all have defaults
role_assignments.id  -> (none)
purchase_entries.id  -> (none)
```

## Root Cause

Migration drift: these two tables were created (or altered) without attaching an identity/sequence to `id`, unlike the rest of the schema. Any code path that relies on the database to generate the key fails. This is the immediate cause of half of ISS-019, and it forced an explicit `MAX(id)+1` workaround when seeding test role assignments during this run — a pattern that is itself race-prone.

## Affected Files / API / Tables

- Schema: `role_assignments.id`, `purchase_entries.id`
- `apps/api/src/panels/admin/catalog-inventory/inventory/...` (`createPurchaseEntry`)

## Recommended Fix

```sql
ALTER TABLE role_assignments  ALTER COLUMN id ADD GENERATED BY DEFAULT AS IDENTITY;
ALTER TABLE purchase_entries  ALTER COLUMN id ADD GENERATED BY DEFAULT AS IDENTITY;
SELECT setval(pg_get_serial_sequence('role_assignments','id'), COALESCE((SELECT MAX(id) FROM role_assignments), 0) + 1, false);
SELECT setval(pg_get_serial_sequence('purchase_entries','id'), COALESCE((SELECT MAX(id) FROM purchase_entries), 0) + 1, false);
```
Then sweep the remaining ~100 tables for the same drift. Note the live `schema_migrations` table is unbaselined, so apply this as a single reviewed migration rather than through a bulk replay.

## Regression Tests Required

- Insert into each table without supplying `id` succeeds
- WH-STK-001 (purchase entry creation)
- Concurrency test: two parallel inserts get distinct ids
